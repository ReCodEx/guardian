# CONTEXT

Domain language and key decisions for the **ReCodEx Guardian** (`recodex-guardian`) — a lightweight Linux containerization tool written from scratch in C++23 to sandbox untrusted code for the [ReCodEx](https://github.com/ReCodEx) automated assignment evaluation system.

This file is the glossary skills should use when naming concepts. The deep rationale lives in `docs/thesis.pdf`; architectural decisions are summarized under [Decisions](#decisions) and should graduate to `docs/adr/` as they're revisited.

---

## Glossary

### Tool concepts

- **Guardian** — this tool as a whole. A modern, ReCodEx-specific replacement for **Isolate** (the Mareš/Blackham IOI sandbox that ReCodEx currently uses).
- **Compatibility mode** (drop-in) — running the Guardian under Isolate's CLI: three independent phases (`--init` / `--run -- prog args` / `--cleanup`) keyed by a caller-supplied `--box-id`, emitting an Isolate-format **meta-file** and `0/1/other` exit codes. State persists between phases on-disk only (the box directory). This is how the ReCodEx Worker drives it. See `docs/adr/0001`.
- **Standalone mode** — running the Guardian under its own single-shot CLI (`--yaml=cfg.yml`): one instance parses one config, runs all its tasks sequentially, and emits per-task **stats-yaml**. Used by the test suites.
- **Instance** — one run of the Guardian: parse config → reserve resources → run tasks → emit metadata. Instances are designed to run concurrently without interfering.
- **Instance ID** (`box_id`) — a unique integer per instance. In compatibility mode it is caller-supplied (`--box-id`, unique per Worker thread); in standalone mode it is configured, else generated. The instance's filesystem root, cgroup path, and UID/GID are all *derived* from it. See `docs/adr/0003`.
- **Sandbox** / **box** — the restricted execution environment (namespaces + cgroups + UID/GID + mounts + filesystem view). "box" is the identifier prefix (`box_uid`, `box_gid`, `box_root`, `box_cgroup`); prose prefers "sandbox". Treat them as synonyms.
- **Box directory** (`/box`) — the single writable working directory inside the sandbox, where the Worker stages job files and the task reads/writes. On the host it is `<box_root>/box`; inside the sandbox it is `/box`. Created at `--init` mode `0700` and handed to the caller (`orig_uid`), then re-owned across a run by the [ownership dance](#decisions). Distinct from **box_root** (the sandbox filesystem root) and from the "box" identifier prefix above: those name the *whole* sandbox, this names *one directory* within it. Isolate's `--init` prints `box_root` to stdout; the Worker appends `/box`.
- **Ownership dance** — how `box/` stays private (`0700`) yet usable by both the unprivileged Worker and the sandboxed task, mirroring Isolate. `--init` chowns `box/` to the caller (`orig_uid`) so the Worker can stage job files; `--run` chowns the `box/` tree to `box_uid` before the task starts (it reads inputs and writes outputs), then, after the task exits, chowns it back to the caller so the Worker can collect outputs. The two run-time chowns use `file_utils::lchown_tree` — a recursive `lchown` that **never follows symlinks** (the tree's contents are attacker-influenced), unlinking nothing (our divergence from Isolate's special-file removal — see [Decisions](#decisions)). Both flips run as root with the box flock held and no live task, so no concurrent mutator can race the walk.
- **Task** — a single unit of execution inside the sandbox: one executable with args, I/O redirection, and resource limits. An instance runs one or more tasks sequentially.
- **Purge** — tearing down the Guardian's *host-wide* state: the shared cgroup parent and the persistent box tree, with every box in it. Deliberately **not** called "cleanup": in compatibility mode `--cleanup` is a per-box phase that destroys *one* box and is part of every normal job. Purge is host-wide, destroys boxes belonging to nobody in particular, and is never part of a job. When you mean one box, say `--cleanup`; when you mean the host, say purge.

### The three processes

An instance is three processes with distinct privilege/responsibility (see [Decisions](#decisions)):

- **Root process** (`root_core`) — reserves *non-isolated* global resources (instance ID, UID/GID, instance cgroup, instance root dir), launches the proxy, then supervises and cleans up. Runs as the launching (root) user.
- **Proxy process** (`proxy_core`) — launched via `clone3()` into the new namespaces/cgroups. Builds the in-sandbox view (mount namespace, filesystem tree, cgroup subtree), then launches and oversees task processes. Becomes PID 1 in the PID namespace.
- **Task process** (`task_supervisor` → `execve`) — runs the untrusted program under all restrictions.

### Configuration vocabulary

- **Directory rule** — a `box-fs.dir-rules` entry mapping a host path (or virtual fs) into a sandbox location with options: read-only (default) / `rw`, `maybe` (mount only if it exists), `fs` (mount a virtual filesystem like procfs), `tmp` (create a temp dir), `dev` (allow devices), `noexec`, `norec` (non-recursive bind). **All task paths (`bin`, `chdir`, `stdin/out/err`, `stats-yaml`) are relative to the sandbox root, not the host.** The **inner path is sanitized** to hold that invariant (matching Isolate's `sanitize_dir_path`): leading slashes are stripped (so the Worker's absolute `--dir=/etc/java` becomes box-relative `etc/java`) and any `..` component is rejected. A **`tmp` rule** does *not* bind the host `/tmp`; it materializes a **fresh, empty, box-owned scratch dir** at the inner path (chowned `box_uid:box_gid`, mode `0700`) and **bind-mounts it onto itself** with `MS_NOSUID|MS_NODEV` — same guarantees as Isolate, but bind-self rather than a separate outer scratch because our `box_root` *is* the pivot root (Isolate's separate scratch + slash→colon mangling is an artifact of its `root/` vs `box_root/` split, which we don't have). Cleaned with the box root at `--cleanup`.
- **Rule override** — caller rules (compat `--dir`, standalone `box-fs.dir-rules`) are matched to the [default set](#configuration-vocabulary) by **inner path**: a caller rule with the same inner path as a default (e.g. the Worker's `--dir=/tmp:tmp` vs the default `tmp:tmp`) **replaces** the default rather than stacking a second mount, mirroring Isolate's in-place override. Isolate's *delete* form (`--dir=in=`, empty right-hand side) and `--no-default-dirs` (`-D`) are **not yet implemented** — the Worker emits neither.
- **Default dir set** — the directory rules applied before any caller rules (unless suppressed). Mirrors Isolate's built-in set (`isolate/rules.c` `init_dir_rules`): `bin`, `dev:dev:norec`, `dev/shm=tmpfs:fs:rw`, `lib`, `lib64:maybe`, `proc=proc:fs`, `tmp:tmp`, `usr` — **plus** our retained `etc` (see [Decisions](#decisions)). Isolate's `box=./box:rw` is *not* a rule for us: the writable `/box` is the pivot root's own `box/` subdir, made at `--init` by `init_box_dir`. `dev` is `norec` so its recursive bind doesn't drag in the host's `/dev/shm`; the fresh `tmpfs` on `/dev/shm` is applied immediately after (order is load-bearing only for this nested pair).
- **Resource limits** (`resource_limits`) — per-task caps: `mem`, `as-size`, `stack`, `cpu-time` (+`extra-time` grace), `wall-time`, `disk-usage`, `processes`, `open-files`, `fsize`, `core`. Enforced via cgroups (mem/cpu/pids), the [disk quota](#linux-mechanisms-as-used-here) (`disk-usage`, standalone only, and box-wide despite being set per task), or rlimits (the rest) — see [Decisions](#decisions). `resource_limits` stores every cap in **canonical units — bytes for sizes, seconds (`double`) for times** — so enforcement code is unit-agnostic. Unit translation happens at the *entry-point constructors*: the **standalone** (YAML) ctor takes bytes and integer seconds directly; the **compatibility** (`cli_options`) ctor converts Isolate's flag units (KB for `cg-mem`/`mem`/`stack`/`fsize`/`core`; **fractional** seconds for `time`/`wall-time`/`extra-time`) into the canonical form. This mirrors the output-side `units::` helpers.
- **Pinning** — restricting every process of a box's `--run` to a caller-given set of CPU cores and NUMA memory nodes. A **box-level** setting, *not* a [resource limit](#configuration-vocabulary): it constrains *where* the box runs, not *how much* it may consume, and it covers the whole box rather than one task. Requested with `--cpuset-cpus=LIST` / `--cpuset-mems=LIST` (named after the kernel files they feed, deliberately not Isolate's `boxN.cpus`/`boxN.mems` or Docker's quota-meaning `--cpus`) and implemented with the [cpuset](#linux-mechanisms-as-used-here) controller. Each flag takes a **cpuset list**: comma-separated ids or `N-M` ranges (`N ≤ M`) and nothing else — a strict subset of what the kernel accepts (its strides, `N` and `all` forms are refused), checked at parse time so the accepted format doesn't vary with the kernel version; an empty list is refused rather than read as "unpinned". Pinning is **exact**: a box runs on precisely the requested cores and nodes, or the `--run` fails (exit 2, `status:XX`) — it never proceeds on a smaller or different set, e.g. when a requested core is offline. The **Worker owns the core map**: the Guardian pins each box as asked but never checks boxes against each other, so overlapping sets are allowed (and may be deliberate, e.g. compilation boxes sharing cores). Compatibility mode only, and only `--run` is pinned: the box's cgroup exists only within a `--run`, so the caller passes the flags on every `--run`; `--init`/`--cleanup` (and standalone) accept and ignore them, like every other compat flag. _Avoid_: affinity (`sched_setaffinity` is per-thread and the task can change it; pinning is kernel-enforced and inescapable), CPU limit (reads as a quantity cap like `cpu.max`), memory pinning (means locking pages in RAM), NUMA pinning (suggests moving the box onto a node's cores; `--cpuset-mems` only restricts which nodes' memory it allocates from — the manual says "CPU and memory-node pinning"). See `docs/adr/0012`.
- **Metadata / stats** — per-task result: `status` (one of `exit_status`: `OK`, `WALL_TIME_EXCEEDED`, `CPU_TIME_EXCEEDED`, `MEMORY_LIMIT_EXCEEDED`, `KILLED`, `NON_ZERO_EXIT_CODE`), exit code/signal, CPU time, memory, wall time. Sourced from **both** cgroup accounting and `getrusage()`. Emitted two ways: **stats-yaml** (`task_stats`, our YAML format) in standalone mode; **meta-file** (Isolate's `key:value` text format — `status: RE/SG/TO/XX`, `exitcode`, `exitsig`, `killed`, `time`, `time-wall`, `cg-mem`, `max-rss`, `csw-voluntary`, `csw-forced`, …) in compatibility mode, written as a *superset* so future ReCodEx can consume extra metrics. **Superset** here means every key Isolate emits, always present, *plus* extra keys under distinct names (the Worker ignores unknown keys) — not a change to Isolate's per-key presence rules. `time` and `cg-mem` are cgroup-sourced, `max-rss` and `csw-*` rusage-sourced; memory in **binary KB** (bytes ÷ 1024). **`cg-mem`** (cgroup subtree peak) and **`max-rss`** (rusage per-process peak) are distinct signals; `cg-mem` is the one key *omitted* when the kernel can't measure it, leaving `max-rss` as the memory signal (see `docs/adr/0006`). Two **discriminators** report *facts* independent of the `status:` verdict: **`killed:1`** whenever the Guardian itself `SIGKILL`ed the task (the `TO` / timeout path), and **`cg-oom-killed:1`** whenever the cgroup's `memory.events` `oom_kill` counter is non-zero (the kernel OOM-killed something). Both can appear on one meta-file.

### Linux mechanisms (as used here)

- **Namespaces** — created via `clone3()` flags. Used: **mount** (`CLONE_NEWNS`), **PID** (`CLONE_NEWPID`, proxy is PID 1), **cgroup** (`CLONE_NEWCGROUP` + `CLONE_INTO_CGROUP`), **UTS**, **IPC**, and **network** (`CLONE_NEWNET`, loopback-only — skipped when `share-net` is set). **User namespaces are deliberately *not* used.**
- **cgroups v2** (`cgroupv2_t`) — the single unified hierarchy at `/sys/fs/cgroup`, driven by creating directories and writing controller files. Enabled **controllers**: `cpu`, `cpuset`, `memory`, `pids` (via `+name` → `cgroup.subtree_control`), on every `--run` whether or not the box is pinned. Key files: `cgroup.procs`, `cpu.max`/`cpu.stat`, `memory.max`/`memory.min`/`memory.peak`, `pids.max`.
- **cpuset** — the cgroup v2 controller that implements [pinning](#configuration-vocabulary), through `cpuset.cpus` (CPU cores) and `cpuset.mems` (NUMA memory nodes). Both take the kernel's list format: comma-separated ids or ranges (`2`, `0,2,4`, `1-4,6`). A cgroup's *effective* set is always within its parent's, and a cgroup without the controller enabled is governed by its nearest ancestor that has it. **v2 pitfall**: the kernel accepts any *possible* core or node, including offline ones (e.g. SMT siblings after `smt/control=off`), and when none of the requested ones can be granted the effective set silently falls back to the parent's — so a successful write does not by itself mean the box is pinned (`kernel/cgroup/cpuset.c`: `cpuset_bind`, `compute_effective_cpumask`). The v1 `cpusets.txt` describes neither behaviour. **Affinity pitfall**: a process entering a cgroup with its own cpuset has its CPU affinity reset to that cgroup's set; kernels ≥ 6.2 (`da019032819a`) intersect it with a `taskset`/`sched_setaffinity` mask instead, older ones discard the mask — and there the first `+cpuset` write at the cgroup root resets the affinity of every process on the host. So a box is pinned with `--cpuset-cpus`, **never with `taskset`** around the Guardian (on ≥ 6.2 the two intersect, silently narrowing the box below what was requested).
- **leaf cgroup** / **proxy_leaf** — empty sub-cgroups the root/proxy relocate themselves into before enabling controllers (controllers can't be enabled in a populated cgroup).
- **rlimits** — per-process `setrlimit()` caps (`RLIMIT_AS`, stack, open files, file size, core, CPU time), inherited across `fork()`. Used for limits cgroups can't express per-process.
- **Credentials** — real/effective/saved UID & GID. Each box gets a dedicated `box_uid`/`box_gid` (= `instance_id + 60000`) for file ownership and privilege drop. `proxy_credentials_manager` switches via `setresuid`/`setresgid`/`setgroups` (`switch_to_box` / `switch_to_user`); order matters. Every id is **range-validated** to the dedicated band `[60000, 65000]` (box_id ≤ 5000): a caller `--box-id`, a standalone `id`, or an explicit `as-uid`/`as-gid` override outside the band is rejected (exit 2), keeping box credentials off privileged and real system accounts.
- **Privilege gate** (`credentials::require_root`) — a fail-fast preamble run once at the top of `root_core::run()`, before the meta-sink is armed or any on-disk state is touched (mirrors Isolate's `get_credentials`). Asserts effective-uid 0 ("Must be started as root"); because the install is mode **4755** (setuid but *not* setgid — ADR 0002), the effective gid is still the caller's on entry, so it `setegid(0)`s to make root-group directory/file creation behave; and `umask(022)` makes creation modes deterministic regardless of the caller's inherited umask.
- **Fsid dance** — before privileged code touches a *caller-supplied* path, it drops the **filesystem** uid/gid (`setfsuid`/`setfsgid`) to the caller for that operation, then restores — Isolate's `switch_fsid_to_caller` / `switch_fsid_back`. Without it, root's DAC-override resolves the path with full privilege. Two guards, two contexts: (1) `meta::detail::fsid_guard` opens the `--meta` file in the *root* process (there `getuid()` is the caller), best-effort — without it a symlink at the `--meta` path could redirect root's create/truncate onto a file the caller cannot reach, and the meta comes out root-owned instead of caller-owned; the fd is authorised at open time so the later writes run as root. (2) `credentials::fsid_caller_guard` probes a `:maybe` rule's outside dir (`is_directory`) in the *proxy*, which runs as real root so the caller ids are passed in explicitly. Box-internal paths (`box/`, the box tree) are *not* caller-supplied and use plain root ops.
- **Drop-priv mount** (`credentials::mount_priv_guard`) — a bind-mount rule (`--dir=in=out`) maps a *caller-supplied* host path into the box, so binding it as full root would let a caller mount a directory it cannot actually reach (root's DAC-override bypasses the check). The guard drops the effective uid/gid to the caller and raises back **only `CAP_SYS_ADMIN`** (the one capability `mount()` needs), so the kernel's path checks apply to the caller — Isolate's drop-priv mount. The saved-set uid stays 0 across the drop so the *permitted* capability set survives; the restore returns to **full root** (our proxy stays privileged — see [Decisions](#decisions)). Only the bind branch is guarded: filesystem mounts (`proc`, `tmpfs`), our box-internal `tmp` self-bind, and the pivot/cgroup mounts have no caller path to abuse and stay root, matching Isolate.
- **Filesystem assembly** — `pivot_root(".", ".")` then `umount2(".", MNT_DETACH)` to swap root (the alternative `chroot` is only mentioned, not used); **bind mounts** (`MS_BIND|MS_REC`) for directory rules and to bind the box root onto itself (pivot_root needs a mount point); **mount propagation** set `rslave` (`MS_SLAVE|MS_REC`) so host→sandbox events propagate but not back.
- **Disk quota** (`quotactl`) — a cap on the disk blocks and inodes the box user owns, enforced by the filesystem's user quota (`QUOTACTL(2)`); needs a filesystem that both supports and *enforces* quotas (e.g. ext4 mounted `usrquota`). A requested cap is **enforced or the phase fails** (exit 2): on a filesystem without quota support, with quotas off, or one that records limits without enforcing them (ext4's `quota` feature mounted without `usrquota`), the box is refused rather than run uncapped — like [pinning](#configuration-vocabulary)'s exactness. Clearing a cap that was never asked for needs no such filesystem. The kernel keeps it against `box_uid`, not against a task or a run, so it counts **every** file the box user owns — including the Worker's staged inputs, which the [ownership dance](#tool-concepts) hands to the box user for the run (as in Isolate, so a cap must cover inputs *and* outputs), and files left by earlier tasks or earlier `--run`s of the same box — and stays in force until it is set again — even past `--cleanup`. In compatibility mode it comes from Isolate's `--quota=<blocks>,<inodes>`: **every** `--init` sets it — clearing it when `--quota` is absent, so a box never inherits a cap left by an earlier box with the same id (Isolate leaves such a stale cap in place) — and a `--run` given `--quota` changes it for that run and every later one, where Isolate applies `--quota` at `--init` only (a `--run` without it leaves the cap alone; `--cleanup` ignores it; the Worker passes it on `--init` only). Compatibility mode has no other way to set it — the Guardian's former `--disk-usage` flag is gone. In standalone mode it comes from the per-task `disk-usage` [resource limit](#configuration-vocabulary): a block cap with no inode cap. Any cap changed mid-box has to allow for the files earlier tasks left behind. Sizes are counted in **quota blocks**, the quota interface's fixed 1 KiB unit — not the filesystem's block size (4 KiB on typical ext4); `--quota`'s first number counts these. _Avoid_: disk limit (reads like `fsize`, which caps a single file).
- **Syscalls of note** — `clone3()` (spawn into namespaces+cgroup atomically), `execve()`, `waitpid()` (root waits on proxy; proxy polls tasks with `WNOHANG`), `getrusage()`.

### Testing

- **Unit test** — a host-side test of pure logic (CLI/config parsing, the box lock) that needs no root; sad paths are process-exit assertions (death tests), since errors go through `terminate()`/`usage_error()` → `exit(2)`, not exceptions (ADR 0005).
- **Workload test** — a test that drives a whole **instance** end-to-end through the binary (needs root + cgroups), covering both the standalone YAML flow and the three-phase compatibility lifecycle.
- **Workload** — an in-box payload program run *inside the sandbox* as a task's executable, written to exercise one specific property. Two families: a **limit probe**, which verifies a resource limit or isolation boundary actually bites (e.g. a program that allocates past the memory cap — what the workload-test tier runs), and a **performance probe**, which exercises exactly one mechanism (compute, syscalls, memory, filesystem, process creation, startup) so [sandboxing overhead](#performance-evaluation) can be attributed to it. Distinct from a **task** (the domain unit of execution): a workload is a task's *executable*, chosen for what it probes.
- **Mock evaluator** (`tests/recodex`) — a stand-in for ReCodEx that replays *real, production-harvested job configs* (C++, Python, C#, Maven) to validate toolchains, limits, and job-shaped task sequences. It drives the Guardian in **standalone mode**, so it deliberately covers no part of the compatibility CLI. Named for what it substitutes (the evaluator's job-running behaviour), not for the **Worker** (whose CLI contract it does not exercise).
- **Compat-phase test** — a workload test that drives the three-phase **compatibility mode** lifecycle (`--init` / `--run` / `--cleanup`) through the binary using Isolate's flag spelling, asserting the meta-file and the box-root-on-stdout contract (`tests/workload/test_compat_phases.py`). It stands in for the Worker at the *CLI* level; validation against the real Worker process happens in ReCodEx's own integration pipeline, not in this repo — see [Decisions](#decisions).

## Decisions

Summarized from `docs/thesis.pdf`. Promote to `docs/adr/NNNN-*.md` when reopened.

- **Custom tool over Docker/Podman** — mainstream runtimes aren't lightweight or precise enough for ReCodEx's resource measurement.
- **Replace Isolate specifically** — Isolate targets the IOI, not ReCodEx; this tool is engineered for ReCodEx's needs.
- **cgroups v2, not v1** — unified, modern resource-management interface.
- **Three-process model (root/proxy/task)** — separation of concerns: privileged global setup + cleanup happens *outside* isolation (root); in-sandbox setup needs to see the whole host fs (proxy); untrusted code runs fully restricted (task).
- **No user namespaces; allocate a dedicated UID/GID per instance instead** — the design assumes root throughout and isolates credentials by deriving `box_uid`/`box_gid` (`instance_id + 60000`) and dropping to them. The **task** process drops irreversibly to `box_uid` (real=effective=saved) via `switch_to_box` right before `execve`, dropping supplementary groups (`setgroups(0, NULL)`) so it inherits none of root's group access.
- **The proxy supervisor currently runs as root — a known divergence from Isolate** (tracked in issue #20). Isolate drops its `box_proxy` to the caller (`orig_uid`) after forking the task, so the monitor watching untrusted code holds no privilege; our `proxy_core` supervises the whole task lifecycle (launch, wall-time `SIGKILL`, cgroup-stat collection, meta reporting) as root. The `switch_to_user` method is the ready-but-unwired call site; a naive drop is blocked because our wall-time kill lives in the proxy and a caller-uid proxy cannot signal the `box_uid` task.
- **The drop-priv bind mount restores to *full* root, not to the caller** — a deliberate consequence of the point above. Isolate's `mount_priv_guard` counterpart ends each bind at `setresuid(orig_uid, 0, orig_uid)` because its proxy is meant to *become* the caller; ours restores `(0, 0, 0)` so the still-privileged proxy can carry on (create the next mount point, chmod an rw bind, run the task lifecycle). When issue #20 wires the proxy drop, this restore target should be revisited alongside it.
- **Derive all per-instance resources from one instance ID** — fs path, cgroup path, and UID/GID are computed from it to avoid collisions. In standalone mode where no ID is supplied, uniqueness is guaranteed by an **atomic `mkdir` claim + retry** (hash of name+time only generates candidates); the allocator-daemon idea is rejected — see `docs/adr/0003`.
- **Isolate-compatible drop-in mode** over the single-shot core, and **setuid-root install with an `isolate` alias** so the non-root Worker can invoke it unchanged — see `docs/adr/0001`, `docs/adr/0002`. Target platform Rocky 9 / RPM — see `docs/adr/0004`.
- **Named the Guardian, packaged `recodex-guardian`** — the former name "Isolator" read as a variant of the tool it replaces, which the `isolate` alias puts right next to it on every host. The artifact carries the `recodex-` prefix to match `recodex-worker`/`recodex-broker`; repo-internal names stay bare (`scripts/guardian.sh`, `GUARDIAN_BIN`). See `docs/adr/0010`.
- **`clone3()` + `CLONE_INTO_CGROUP`** — atomically place the child into its target cgroup at creation; with `CLONE_NEWCGROUP` that cgroup becomes the namespace root.
- **Relocate to leaf cgroups before enabling controllers** — controllers can't be enabled in a populated cgroup.
- **Enforce memory with `memory.max` + `memory.min=max` + swap OFF** — with swap on, the kernel reclaimed memory and let the process exceed `memory.max`; `memory.min=max` alone didn't help. Only disabling swap gave consistent termination at the limit. *(Documented kernel pitfall.)*
- **cgroups for mem/cpu/pids, rlimits for the rest** — rlimits can't measure cumulative usage across a process hierarchy.
- **`--mem` drives the cgroup memory limit, not `RLIMIT_AS`** — a deliberate deviation from Isolate (where `--mem` caps per-process address space): both `--mem` and `--cg-mem` express a memory cap and we enforce memory via the cgroup, consistent with the cgroups-first split above. Our own `--as-size` flag remains `RLIMIT_AS`.
- **Detect memory-limit hits from `memory.events` `oom_kill`, not a peak-vs-limit comparison** — the kernel's OOM-kill counter is authoritative and false-positive-free; comparing the cgroup peak against the limit can misfire at the boundary. `memory.events` predates `memory.peak` and is reliably present on the el9 target, so no heuristic fallback is kept.
- **Measure wall time externally in the proxy** — no kernel-enforced wall-clock limit exists; the proxy polls `waitpid(WNOHANG)`, sleeps to avoid busy-waiting, and `SIGKILL`s on overrun. The interval is timed against the **monotonic clock** (`std::chrono::steady_clock` → `CLOCK_MONOTONIC`), never the wall-clock/civil-time clock: an NTP step or slew would otherwise postpone a kill, time out a well-behaved task, or land in the `time-wall` a student sees.
- **Combine cgroup + `getrusage` stats** — cgroup gives subtree-wide totals (catches multi-process/threaded use); rusage adds peak RSS and user/system CPU.
- **Build the sandbox fs via mount namespace + bind mounts + pivot_root**, with a fresh `cgroup2` remounted inside so task handlers see only the sandbox's cgroups.
- **Mount propagation = slave-recursive** — blocks sandbox→host mount events, narrowing a known vulnerability surface.
- **Network: full isolation (loopback-only) by default, or full host access via `share-net`** — only two modes today; restricted inter-sandbox networking (veth) is future work.
- **Task I/O redirects are opened as the box user** — in the task process the order is rlimits → drop to `box_uid` → `chdir` → open `--stdin`/`--stdout`/`--stderr`, matching Isolate's `box_inside`. Opening the redirect files *after* the privilege drop means `--stdin` respects box-user permissions (a task can't read a file it otherwise couldn't) and `--stdout`/`--stderr` files are created box-owned, not root-owned.
- **Default dir set tracks Isolate's, minus `box` plus `etc`** — we mirror Isolate's built-in defaults so a box behaves identically without caller rules, with two intentional differences: `box` is not a rule (our `/box` is the pivot root's own subdir, made at `--init`), and we retain an extra read-only `etc` bind that Isolate lacks. The real Worker job configs mount `/etc` *surgically* (`etc/java:maybe`, `etc/alternatives=…:maybe`), so the broad `etc` default is a deliberate divergence kept for pragmatism; the precise dependency it was added for is unconfirmed, and it can be dropped once compat `--dir` wiring lets the Worker supply its own `/etc/*` rules.
- **An explicit zero limit is enforced or refused — never silently read as "no limit"** — Isolate guards most caps on a non-zero value (`if (memory_limit)`, `if (fsize_limit)`, …), so a `0` there quietly means *unlimited*. We don't reinterpret zeros. For `mem`/`cg-mem`, `fsize`, `open-files` and `as-size` an explicit `0` is **enforced literally** — a caller asking for zero gets zero. The one exception is the [disk quota](#linux-mechanisms-as-used-here), where the kernel itself has no zero limit (its 0 *is* "no limit"): a 0 in either number of `--quota` or in `disk-usage` leaves that cap unlimited, and the two numbers of `--quota` are independent, so `--quota=0,100` still caps inodes — where Isolate sets no quota at all. For `stack` and `processes`, where a literal zero is not merely strict but *meaningless* (no stack at all leaves the task unable to `execve`; a process cap of 0 only duplicates `=1`, since the pids controller fails forks rather than killing the task), it is **refused** as a usage error (exit 2). Asking for no limit means omitting the flag — or, for processes, the bare `--processes` the Worker emits, which still means unlimited. `core` needs no rule: 0 is a real limit there for both of us. An **unset** `stack` is the one cap applied unconditionally, as `RLIM_INFINITY`, because Isolate always sets `RLIMIT_STACK` and inheriting the caller's ~8 MiB instead would flip verdicts on deep recursion. A deliberate divergence — Isolate accepts every one of these forms silently — reachable only by a config that actually specifies 0, which no Worker default does. See `docs/adr/0008`, #21, #22.
- **Real-Worker validation belongs to ReCodEx's own integration pipeline, not to this repo** — an in-repo tier that drove the real Worker (through a stub broker, against an installed alias build) was built and then **removed**: standing up a Worker clone, its judges, a ZeroMQ broker double and an el9 host is exactly the harness ReCodEx already maintains, and duplicating it here bought smoke-testing confidence at the price of a second integration harness to keep alive. What this repo owns instead is the **CLI contract** — the compat-phase workload tests assert Isolate's flag spelling, meta-file format, exit codes and the box-root-on-stdout handshake without any ReCodEx component present. The cost accepted: nothing here catches a mismatch that only appears when the Worker itself is the caller (its own flag emission and meta-file parsing), so that class of regression surfaces in the ReCodEx pipeline rather than locally.
- **No boot service; `--run` self-arranges the shared cgroup parent** — the Guardian ships no systemd init service and no separate cg-keeper helper (a divergence from Isolate). The shared `recodex-guardian` cgroup parent (`/sys/fs/cgroup/recodex-guardian`) is created, and its `cpu`/`memory`/`pids` controllers enabled, **lazily and idempotently** at the start of `--run`/standalone — a small symmetric extension of the root- and instance-level enables already performed there. This replaces the former boot-time `guardian_init.sh`, keeps install zero-config, and fits the daemonless model (ADR 0005). The persistent box tree lives at **`/var/lib/recodex-guardian/boxes`** and the box locks at `/run/recodex-guardian/locks`. See `docs/adr/0007`.
- **Pin the whole box, from the command line, exactly — three divergences from Isolate** — Isolate reads per-box `cpus`/`mems` from its config file and pins only the *task* (the task writes itself into the cpuset cgroup). We take [pinning](#configuration-vocabulary) from the caller on every `--run` (the Worker owns the core map; there is no config file), pin root supervisor, proxy and tasks alike so the supervisor's setup/teardown work never lands on another box's cores (free during the task: both supervisors sleep until it exits), and fail the run rather than accept the kernel's silent fallback when a requested core or node can't be granted. See `docs/adr/0012`.

## ReCodEx integration constraints

- **Drop-in for ReCodEx's process-isolation subsystem** — must replace and extend `Isolate`. Real Worker integration is still pending (both sides need CLI/output-format adjustment) and is validated in ReCodEx's own pipeline, against an `-DISOLATE_ALIAS=ON` install — see [Decisions](#decisions).
- **Worker runs jobs as a task DAG** — compile → run → evaluate ("Judges") with dependencies; some tasks are `fatal-failure`. The "instance = sequential related tasks" model mirrors this.
- **Shared writable dirs across job phases** — phases run as *separate* Guardian invocations sharing files. This once forced `box/` to mode `0777`; **resolved** by the [ownership dance](#glossary) (#13), which keeps `box/` at `0700` and re-owns it between the caller and `box_uid` across a run, so no world bits are ever needed.
- **Ownership dance chowns in place, without unlinking special files** — Isolate's `chowntree` *removes* non-regular/non-dir entries (fifos/sockets/symlinks) during the ownership flips (default `special_files=false`); we `lchown` them in place instead. The load-bearing property is no-follow (a planted symlink cannot redirect the chown), which `lchown_tree` keeps; `chown` already strips setuid/setgid bits off regular files, and the box user cannot create device nodes (no `CAP_MKNOD`). Not unlinking avoids ever destroying a caller-staged or task-produced entry as a side effect of a chown, and the whole tree is `rm -rf`'d at `--cleanup` regardless.
- **Offline, diverse toolchains** — validated on C++, Python, C# (.NET). Pitfalls baked into config behavior: GCC needs the host `PATH` inherited and a `LD_LIBRARY_PATH` derived from `gcc -print-search-dirs`; C# uses a custom offline `/opt/dotnet` pointing at `Roslyn/csc.dll`.
- **Three test tiers** — **unit tests** (host-side, no root) cover pure logic: CLI/config parsing and the box lock; **workload tests** drive a whole instance end-to-end through the binary (need root/cgroups), running **workloads** (in-box payload programs) to verify a limit or isolation boundary actually bites, and covering the three-phase **compatibility mode** lifecycle in [compat-phase tests](#testing); the **mock evaluator** (`tests/recodex`) replays real job configs through *standalone* mode. No tier runs a ReCodEx component — validation against the real Worker is ReCodEx's pipeline's job, see [Decisions](#decisions). See the [Testing](#testing) glossary.

## Conventions

- C++23, header-heavy (`src/*.hpp`), built with CMake (`scripts/guardian.sh build`); logging via a thin `logs::` wrapper over `std::format`, writing to **stderr** (stdout is reserved for `--init`'s box-root path) — see `docs/adr/0002`.
- Class names are snake_case: `root_core`, `proxy_core`, `proxy_connector`, `proxy_mount_manager`, `dir_rule_supervisor`, `task_supervisor`, `cgroupv2_t`, `*_credentials_manager`.
- Fatal errors go through `terminate(...)` (log + `exit(2)`, the Guardian's internal-error code — ADR 0005).
- Requires root; needs a cgroupv2-enabled kernel. The shared cgroup parent is self-arranged on first `--run` (ADR 0007, no init step); `scripts/guardian.sh purge` tears the shared cgroup tree + box tree back down.
- One script owns the artifact lifecycle: `scripts/guardian.sh MODE` (`build`, `package`, `install`, `uninstall`, `purge`). Source installs and RPM installs are kept strictly apart — `uninstall` refuses to touch files an RPM owns.

When you name a domain concept in an issue, refactor, or test, use the term as defined above. If a concept isn't here yet, that's a signal — either reconsider the wording or note the gap (e.g. via `/grill-with-docs`).
