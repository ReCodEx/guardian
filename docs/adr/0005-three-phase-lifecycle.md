# Three-phase compatibility lifecycle: phase responsibilities, meta channel, and exit codes

Compatibility mode (ADR 0001) is three independent process invocations sharing state only on-disk. This ADR records how the existing single-shot flow in `root_core` (which did credentials → create dir → cgroup → spawn proxy → wait, all in one process) is split across `--init` / `--run` / `--cleanup`, and the three non-obvious decisions that split forces. All three phases are methods on a single `root_core` selected by a `mode` enum parsed from `cli_options`; standalone (`--yaml=`) keeps the monolithic flow.

## Per-phase responsibilities

- **`--init`** — derives per-box identifiers from `--box-id`, takes the lock (`O_CREAT`), creates the box root directory and the writable `box/` subdir (`0777`, owned `box_uid:box_gid`), prints **box_root** to stdout (the Worker appends `/box`), and sets the lock's `is_initialized` bit. It does **no** mounting and touches **no** cgroup.
- **`--run`** — takes the lock (must already be initialized, else exit 2 "Box not found"), **creates the instance cgroup** (+ leaf subtree) immediately before `clone3` (required by `CLONE_INTO_CGROUP`), builds namespaces/mounts/`pivot_root`, and runs the single program. It removes any stale same-box-id cgroup first so a repeated `--run` is safe.
- **`--cleanup`** — `rm -rf`s the box dir, removes the cgroup, and `ftruncate`s the lock. Idempotent: a missing box/cgroup/lock is success (exit 0).

**Cgroup is created at `--run`, not `--init`** — a deliberate divergence from upstream Isolate (whose persistent cg-keeper creates it at init). In our daemonless model the cgroup path is a pure function of `--box-id` recomputed each phase (ADR 0001), so there is no benefit to splitting cgroup creation (init) from population (run) across two processes; keeping the whole cgroup lifecycle inside `run → cleanup` lets us lift the existing `cg_mngr_` flow unchanged and keeps `--init` from needing the cgroup controllers writable.

## Meta channel: pipe from proxy to root, root as sole writer

The Worker passes `--meta=<host path>` and parses Isolate's `key:value` meta-file. That path is **not** mounted inside the sandbox and the proxy is in its own mount namespace after `pivot_root`, so the proxy cannot write it — and the proxy currently `exit(0)`s, losing the task's real status before root's `waitpid`. We therefore open a `pipe2` in the proxy connector **before** `clone3` (the cloned proxy inherits the fd); the proxy serializes the single task's `task_stats` into it and root, after `waitpid`, writes the Isolate-format meta to the host path. **Root is the sole meta writer.** This is distinct from standalone mode, where the *task* writes our **stats-yaml** to a box-relative path — two separate metadata sinks, deliberately. The alternative (encoding the task's exit code into the proxy's own exit status) was rejected: it caps the channel at 8 bits + a signal, and the full meta-file (`cg-mem`, `time`, `max-rss`, …) would tear it out and build the pipe anyway. For this slice only `status`/`exitcode`/`exitsig` are serialized, but through the real channel.

## Exit codes and the internal-error meta

We follow Isolate's convention: **0** = program ran and exited 0; **1** = program ran but result ≠ OK (nonzero exit / signal / timeout), meta written with a `status:` line; **2** = Isolator's own failure (bad flags, setup failed, box-not-found). The 0-vs-1 decision lives in **root** and the pipe doubles as the success signal: a complete `task_stats` record ⇒ write meta, exit 0/1; the pipe **closing empty** (proxy hit a fatal error during setup) ⇒ exit 2. `terminate()` changes from `exit(1)` to `exit(2)` accordingly — it is the internal-error path by definition (safe for standalone, whose tests assert on the result YAML, not the exit code).

On an internal error in compat mode we still write a meta-file with `status:XX` + `message:` (the Worker reads it for diagnostics). Because `terminate()` is called from deep in both the root and proxy processes, it cannot be handed the `--meta` path directly. Instead root registers the meta path in a small process-global **meta-sink** after parsing `--meta`; `terminate()` formats its message once, logs it to stderr, and — if the sink is set — writes `status:XX`/`message:` before `exit(2)`. The proxy is a `clone3` child that inherits root's state, so it **explicitly disables the meta-sink right after `clone3`**: only root ever writes the host meta-file (proxy-side `terminate()` just exits 2, and root turns the resulting empty pipe into the `status:XX` meta). We chose the meta-sink over making `terminate()` throw and catching per-mode in `main()`, because exception unwinding across the `clone3` child boundary and through `noexcept`/destructor paths is exactly the fragile case we want to avoid.

## Refinement (B2): `--init` lock ordering and re-init semantics

`--init` sequences the lock around the box build as **reset-first / set-last**: it takes the flock, clears the `is_initialized` bit *before* touching the box tree, builds the box, and sets the bit *only at the very end*. The bit therefore means "an `--init` ran to completion" — a `--init` that crashes partway leaves it at 0, so a later `--run` correctly sees an un-initialized box rather than a half-built one (this mirrors upstream Isolate, which resets the record on init and writes `is_initialized = 1` last).

Two decisions here diverge from Isolate deliberately:

- **`--init` on an already-initialized box is a hard error (exit 2), not a silent rebuild.** Isolate's `init()` calls `do_cleanup()` unconditionally and rebuilds; we instead read the bit up front and `exit(2)` if it is already set. A double-`--init` without an intervening `--cleanup` is a caller (Worker) bug, and failing loudly surfaces it rather than silently destroying a box a prior phase populated. This is safe precisely because the **flock**, not the bit, guards a box *in use*: a live `--run` holds the flock, so a concurrent `--init` blocks/fails on the flock and never reaches the bit check — meaning any `--init` that *does* acquire the flock has no concurrent phase to protect, and an already-set bit can only mean a completed-but-idle box.

- **A crashed-init stray tree (bit 0, box dir partially present) self-heals rather than wedging.** The re-init guard keys on the *bit*, not the directory; a box with the bit at 0 proceeds, and `--init` `fs::remove_all`s any pre-existing box root before creating a fresh one (absorbing crash debris, as Isolate's leading `do_cleanup()` does). Only a *completed* init (bit 1) refuses.

The `0777` mode on `box/` remains the documented insecure status quo (CONTEXT.md's top security item); B2 wires the create/chown/chmod mechanism but defers tightening the mode to a dedicated security step.

## Refinement (C1/C2): meta record wire format, exit-code mapping, and the meta-sink

Stage C makes the meta channel concrete. Decisions settled while implementing:

- **The wire record is `task_stats` itself, sent as a fixed-size blob.** Rather than a second result struct, the proxy writes `task_stats` (which is trivially copyable — scalars + one enum + one pointer) straight down the pipe; root reads exactly `sizeof(task_stats)` and never dereferences the `config_` pointer (the proxy zeroes it before writing; a `static_assert(std::is_trivially_copyable_v<task_stats>)` guards the day someone adds a `std::string` field). The **fixed size is what makes the exit-code contract robust**: a read of exactly `sizeof` ⇒ complete record (exit 0/1 per the mapping below); a read of `0` (EOF) ⇒ proxy died before writing ⇒ `status:XX`, exit 2; a partial read (`0 < n < sizeof`) ⇒ proxy died mid-write ⇒ `status:XX`, exit 2. The proxy's `waitpid` status is advisory (logging only) — the pipe is the source of truth.

- **Pipe fd discipline: `pipe2(O_CLOEXEC)`, proxy is sole writer.** The write-end must not survive into the task's `execve` (a leaked fd into untrusted code would also defeat the EOF-means-failure signal), so both ends are `O_CLOEXEC`; root `close()`s the write-end right after `clone3`; the proxy holds the only write-end and writes the record after `waitpid`-ing its task, before its own `exit(0)`. `proxy_core` no longer computes an exit code (the crude B4 `exit(0/1)` scan is deleted) — it always `exit(0)`; **root** owns the 0/1 decision from the record.

- **`proxy_core` receives a capability, not a mode.** It takes an `int meta_write_fd` (default `-1`): it writes the single task's `task_stats` iff `fd >= 0`, otherwise stays exactly as standalone left it (the task writes its own stats-yaml; the proxy exit code is ignored). `proxy_connector` owns the pipe lifecycle and only opens it on the compat `--run` path. This keeps the standalone-vs-compat split out of `proxy_core` — it is a channel, not a `run_mode`.

- **`exit_status` → Isolate meta mapping lives in root, in a dedicated Isolate-meta writer** (separate from the standalone `generate_stats_yaml`, which stays YAML-only). Checked in order: `WALL`/`CPU` → `status:TO`; `MEMORY` → `status:SG`; `signalled` → `status:SG` + `exitsig:<sig>`; `exit_code != 0` → `status:RE` + `exitcode:<code>`; else (normal, code 0) → **no status line** + `exitcode:0`. Two deliberate drop-in nuances: an OK run **omits `status:` entirely** (Isolate does; our own stats-yaml writes `status: OK`, but compat mode matches Isolate), and **`MEMORY_LIMIT_EXCEEDED` maps to `SG`, not a bespoke code** — a memory hit is an OOM-kill (SIGKILL), and ReCodEx discriminates it via `cg-oom-killed:1` (a deferred metric line), not the status. This slice wires only `status`/`exitcode`/`exitsig`; the metric lines (`time`, `cg-mem`, `cg-oom-killed`, `max-rss`) slot into the same table later.

- **The C2 meta-sink is armed for any compat phase given `--meta`** (init/run/cleanup), not just `--run` — a failed `--init`/`--cleanup` the caller pointed `--meta` at leaves a `status:XX` meta, matching Isolate; standalone never arms it (no `--meta`, and its tests expect a bare `exit(2)`). The single Isolate-meta writer owns both the result write and the sink's `status:XX`/`message:` write.

- **Write-once discipline.** Meta writes are **best-effort**: on I/O failure the writer logs to stderr and returns — it must never call `terminate()`, which would re-enter the sink and recurse. Root **disarms the sink immediately after** the authoritative result write, so a later teardown `terminate()` cannot clobber a real `OK`/`RE`/`SG`/`TO` result with `XX`; a crash after the result is recorded still exits 2 but leaves the honest task outcome intact.

- **Deferred: a dedicated error pipe.** For a proxy-side `terminate()` (mount/`pivot_root`/in-box cgroup failure), root sees only the empty pipe and writes a **generic** `status:XX` + `message:` — the proxy's specific error reaches stderr but not the meta-file. Isolate forwards it via a second error pipe (`write_errors_to_fd`); we deliberately did **not** fold error text into the stats pipe (it would break the fixed-size framing). The dedicated error pipe is a purely additive, non-breaking enhancement left for later.

- **The meta-sink lives in its own config-free header (`meta_sink.hpp`), deliberately split from `meta_file.hpp`.** `terminate()` must write `status:XX` on the way out, but `config.hpp` already includes `terminate.hpp` — so putting the sink in `meta_file.hpp` (which pulls `config.hpp`) would make `terminate.hpp → meta_file.hpp → config.hpp → terminate.hpp` a cycle. The sink and the XX/best-effort file writers genuinely need only a path and a string, not `task_stats`, so they sit in a low-level `meta_sink.hpp` that `terminate.hpp` includes; `meta_file.hpp` includes *it* and adds the `task_stats`-dependent record I/O and result mapping. Merging the two back together reintroduces the cycle — the split is load-bearing, not organizational. The sink itself is a function-local `static std::optional<fs::path>` (the `logs::current_level()` idiom), armed once in `root_core::run()` when `--meta` is present and disabled as the first statement of the `clone3` child branch.

- **Parse-time failures are meta-less.** `usage_error()` (bad flags, conflicting modes, missing `--box-id`) `exit(2)`s during `cli::parse`, *before* `root_core::run()` arms the sink — so a malformed invocation writes no meta-file. This matches Isolate (argument errors precede opening the meta path) and is the intended boundary: an invocation the Worker constructed wrong is not a sandbox result.
